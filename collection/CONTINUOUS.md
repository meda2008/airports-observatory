# 连续采集执行契约

入口：`runWorkflow({continuous:{journalFile,runs,handlers,onProgress}})`，或直接导入 `runContinuous`。`runs` 是明确授权的统一流程参数列表，顺序执行；每次只消费一个页面任务或一个未支付订单任务，减少浏览器单次执行超时风险。

固定动作：读取缺项与原件 → 按哈希复用 → 采集未读入口 → 归属检查 → 已授权登录注册 → 零余额与原有订单检查 → 创建临时未付订单 → 读取渠道 → 取消并验证 → 语义复核 → 入库、构建和发布核对。具体动作仍由原统一流程执行，总控不重写这些安全边界。

`collecting`、发现、订单采集等中间状态会自动续跑。`awaiting_semantic_review`、`backend_pending`、搜索回执等状态由同名 `handlers` 接口处理；只有实际完成依赖并返回 `{resolved:true}` 才续跑。没有接口或依赖尚未解决时，记录该运行断点并继续其他运行。不能返回虚假复核批准。后台作业仍由 `scripts/unified-worker.cjs` 执行；本入口没有独立浏览器守护服务，调用所在进程退出后需要用同一journal恢复。

已终结、已阻塞运行在恢复时不会自动重复。外部证据发生变化后应建立新的明确运行及campaign，不修改已冻结范围和权限。浏览器超时后保留底层断点；本总控错误记录不会把失败改写为成功。

取消失败会立即返回 `cleanup_required_stop_campaign`，禁止继续新增订单。付款始终禁止，账户余额不明、条款或人机验证不自动放行。

`runnable_queue_exhausted_with_gaps` 表示当前可执行队列耗尽，不能对用户宣称数据补齐。仅所有运行实际报告 `dataComplete:true` 时标记 `data_complete`。当前原统一流程尚未具备业务字段全量完成的自动证明，所以通常保留缺项状态。

验证：`node --test tests/continuous-workflow.test.cjs`。测试证明调度与恢复契约，不代表真实机场采集、支付渠道或部署验收。

运行接线：`runtimeHandlers({runDirectory})`提供复核请求与后台回执接口；以`node scripts/continuous-backend.cjs CAMPAIGN.json`启动后台作业消费者，CAMPAIGN文件包含`runs:[{runId}]`，写入`stopWorker:true`可结束消费者。复核读取本运行`review.json`，未审核时写`review-request.json`，不自动批准。后台同时支持入库作业的`result.job`与发布作业的`result.release`回执。

浏览器调用使用`maxSteps:1`作为调度时间片，`execution_yielded`和`waiting_for_dependencies`需要调用方继续驱动同一journal；这不是数据完成或永久阻塞。每个时间片会落盘，恢复不依赖REPL变量。已阻塞项只有`resumeBlocked`明确检查外部变化后才能重新启用，保留旧错误事件。浏览器执行仍依赖当前受控浏览器连接，后台消费者只负责入库、构建与发布，不冒充浏览器守护进程。
